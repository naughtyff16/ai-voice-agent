## 2. Purpose

This document specifies the Platform Admin (cross-tenant "super admin") API surface and its DB-enforced trust model, as that model actually exists at Alembic head `109_5B7` — not as it existed at `105_5B4`/`106_5H3`/`108_5B6`. Platform Admin capability is **narrow and guarded by design**: every mutating cross-tenant action goes through a `SECURITY DEFINER` PostgreSQL function that itself re-checks identity, and every sensitive read (recording/transcript content) requires a durable, purpose-scoped break-glass grant plus an atomic, in-transaction audit write. `app_platform_admin`'s own row-level/table-level grants are deliberately close to nothing outside those guarded functions.

## 3. Scope

In scope: platform-admin organization support (list/detail/suspend/reactivate), quota overrides, durable purpose-scoped break-glass, cross-tenant sensitive-media support for **both recordings and transcripts**, refund reservation (settlement is a reconciler-only concern described here for completeness but not itself a Platform Admin action), platform-wide provider health / cross-tenant analytics (via the frozen 6L projection architecture), billing administration support built on existing guarded functions, feature-flag/system-config reconciliation, user/session/API-key support, and integration/workflow diagnostics reconciliation.

Out of scope (see §4, §46): manual `billing_accounts` suspend/reactivate override; workflow execution start/replay from the Platform Admin surface; raw key/hash/token/secret exposure; arbitrary pricing mutation; feature-flag CRUD (no persistence exists — see §54).

## 4. Non-Goals

- **Platform-admin transcript-content access is NOT deferred.** The prior draft's §4/§46 said otherwise; that was true only through `106_5H3`. As of `107_5B5`, `voice.fn_platform_access_transcript(...)` is live, guarded identically to recording access (session_user check + `SENSITIVE_MEDIA_ACCESS` break-glass check + resource-ownership cross-check + atomic audit write). See §21.
- No manual billing-account suspend/reactivate override in V1 (`DEC-6M-02`, §24, FINAL).
- No Platform Admin capability to mark a refund `SUCCEEDED`/`FAILED` directly; only `app_billing_reconciler` may settle or fail a refund (§19-§20).
- No restoration of `workflow.fn_start_workflow_execution` to `app_platform_admin` (frozen by 6I §66; see §55).
- No feature-flag CRUD over nonexistent storage (§54).
- No hidden/non-transparent Platform Admin support actions against tenant data (`DEC-6M-03`, §24 — tenant audit visibility stays transparent by default).
- No transactional-table analytics queries; platform financial/health analytics reuse the frozen 6L `AnalyticsReadPort`/projection architecture (§52).

## 6. Terminology

- **Platform Admin (human role)** — an operator role, authenticated through 6B's normal authN path, whose *application-layer* JWT/session carries a claim that lets the backend route its DB session through the `app_platform_admin` DB credential and set `app.is_platform_admin = 'true'`.
- **`app_platform_admin` (DB principal)** — the actual authenticated PostgreSQL role. Trusted only because `session_user` cannot be forged by SQL running inside a session (unlike a GUC).
- **`app_billing_reconciler` (DB principal)** — a `LOGIN` role with **no table privileges on any billing table and no `BYPASSRLS`**; its only capability is `EXECUTE` on `fn_platform_settle_refund`/`fn_platform_fail_refund`. Used exclusively by the backend's payment-provider-webhook/reconciliation worker, never by a human-facing route.
- **Break-glass grant** — a durable row in `organization.break_glass_grants`, purpose-scoped, time-bounded, releasable.
- **Purpose** — one of the six allow-listed values (§11); required on every break-glass grant and re-checked per access.

## 9. Architecture Principles & Invariants

1. Every cross-tenant *mutation* goes through a `SECURITY DEFINER` function; the Platform Admin application layer never issues raw `INSERT`/`UPDATE`/`DELETE` against a tenant table.
2. `app_platform_admin`'s direct table grants are minimal: `SELECT` only on `organization.organizations`, `billing.refunds`, `billing.payment_attempts`, `billing.quota_configs`; full DML on `billing.invoices` (pre-existing 6K support capability, not a 6M-introduced bypass); **zero** grant on `voice.recordings`, `voice.transcript_segments` (parent and, since 108, all child partitions), `voice.conversations`, `voice.turns`, `voice.transcripts`.
3. Identity trust binds to `session_user`, never to `current_user` (which changes to the owning role inside `SECURITY DEFINER`) and never to a session GUC alone (self-forgeable). This is the same rationale `072_5J.sql`'s `audit.fn_insert_audit_event()` already relies on.
4. Refund *settlement* truth comes only from a verified payment-provider response, consumed only by `app_billing_reconciler` — never by a human/admin route (see §19-§20).
5. Sensitive voice content (recording bytes, transcript text) requires a **purpose-bound, durable, releasable** break-glass grant, re-checked on every access, in addition to the DB-principal check.
6. **Audit-write atomicity is not uniform across the whole platform.** Functions introduced or touched by `107_5B5` (break-glass grant/release, org suspend/reactivate's audit line, sensitive-media access, refund settle/fail) write their audit event with `PERFORM audit.fn_insert_audit_event(...)` **inside the same transaction and function body** as the state change they describe — this is atomic by construction. Functions predating this pattern (`billing.fn_billing_apply_credit`, `billing.fn_create_billing_adjustment`, and `102_5H2.sql`'s four CPA functions — see §37, §57) have **no internal audit call at all**; auditing for those, if performed, happens as a separate, non-atomic, application-layer call, following the older `087_5B1.sql` precedent. The prior draft's §9/§30 asserted uniformly "no fused audit write"; that was accurate for 105/106 but is now false for 107_5B5's own functions. Both statements are true of their respective function sets — this document tracks the split explicitly rather than generalizing either way. **This pass's own new guarded/wrapper functions (§65.1-§65.6, migration `109`) all follow the `107_5B5` atomic pattern**, including the wrappers that sit in front of the non-atomic pre-existing functions just named — the wrapper's own transaction, not the wrapped function's, is what makes the resulting Platform-Admin-initiated call atomic (§65, §30).
7. Tenant break-glass access is transparent to the tenant by default (`DEC-6M-03`, §24) — no hidden support actions.
8. Cross-tenant analytics reads a projection table, never `analytics.analytics_events` or a 5B–5I OLTP table directly (6L §9); 6M inherits this, it does not re-derive its own aggregation.

## 11. Break-Glass Canonical Model

Table `organization.break_glass_grants` — exact column list: `id, organization_id, admin_user_id, justification, session_id, issued_at, expires_at, status ('ACTIVE'|'RELEASED'), released_at, released_by, purposes TEXT[]`. There is no `ttl_seconds`, `granted_at`, or `revoked_at` column; `ttl_seconds` is a *parameter* to `fn_break_glass_grant` used only to compute `expires_at` at insert time. Release is recorded via `status`/`released_at`/`released_by`.

Purpose vocabulary (allow-listed, exactly six values): `SUPPORT_GENERAL`, `SUPPORT_BILLING`, `SUPPORT_ORG_LIFECYCLE`, `SUPPORT_QUOTA`, `SENSITIVE_MEDIA_ACCESS`, `SUPPORT_SECURITY_INCIDENT`. Wildcards are rejected at issuance by `chk_bgg_purposes_no_wildcard` against exactly four literal values: `'*'`, `'ALL'`, `'ALL_ACCESS'`, `'SUPER_ADMIN'`. `purposes` is immutable after insert — only `status`/`released_at`/`released_by` may change.

`organization.fn_break_glass_check(p_grant_id UUID, p_admin_user_id UUID, p_organization_id UUID, p_session_id TEXT, p_required_purpose TEXT) RETURNS BOOLEAN` — `SECURITY DEFINER`, never raises, returns `FALSE` on any of: caller not `is_platform_admin()`; grant not found; `status <> 'ACTIVE'`; `expires_at <= NOW()`; admin/org/session mismatch; `p_required_purpose` null/empty; purpose not in the grant's `purposes` array. `EXECUTE` was granted to both `app_api, app_platform_admin` at introduction (105_5B4) but **narrowed by 107_5B5 to `app_platform_admin` only** (`REVOKE EXECUTE ... FROM app_api`) — an ordinary tenant session has no reason to call this function at all.

## 12. Break-Glass Issuance Contract

`organization.fn_break_glass_grant(p_organization_id UUID, p_admin_user_id UUID, p_justification TEXT, p_ttl_seconds INTEGER, p_session_id TEXT, p_purposes TEXT[]) RETURNS UUID` — `SECURITY DEFINER`, `app_platform_admin`-only (`app_api` explicitly revoked by 107_5B5). Validates: caller is `is_platform_admin()`; `p_ttl_seconds` in `[60, 86400]`; `p_purposes` non-empty and `<@` the allow-list. Writes the grant row, then `PERFORM audit.fn_insert_audit_event(...)` in the same transaction with action_kind `BREAK_GLASS_GRANTED`, `resource_snapshot = {grant_id, purposes, ttl_seconds}`. A legacy 5-arg overload (no `p_purposes`) still exists for the pre-purpose-scoping call shape but is likewise `app_platform_admin`-only and atomically audited.

`organization.fn_break_glass_release(p_grant_id UUID, p_admin_user_id UUID) RETURNS ...` — fetches `organization_id` under lock to bind tenant context, sets `status='RELEASED'`, `released_at`, `released_by`, atomically audits `BREAK_GLASS_RELEASED`. `app_platform_admin`-only.

**Endpoint: REUSED EXISTING 6B ENDPOINT.** `POST /api/v1/platform-admin/organizations/{organization_id}/break-glass` (issue), `POST /api/v1/platform-admin/break-glass/{grant_id}/release` — both are 6B's own, already-frozen routes (`6B-Authentication-and-Authorization-API.md`); this document does **not** define a competing `POST /api/v1/platform-admin/break-glass` route (an earlier draft of this section did so in error — corrected this pass, see §5 of the governing remediation instructions). 6M's contribution is limited to the 105/107 purpose-scoping semantics layered onto 6B's existing request/response contract (`p_purposes`, `p_session_id`) — the canonical path, and the org-id scoping on issuance, remain 6B's.

## 13. Break-Glass Purpose Scoping — Design Rationale

Purpose scoping exists so that a break-glass grant issued for, e.g., `SUPPORT_BILLING` cannot be silently reused to justify a `SENSITIVE_MEDIA_ACCESS` read. Every guarded function that consumes a break-glass grant passes its own fixed, hardcoded `p_required_purpose` literal to `fn_break_glass_check` (e.g. `voice.fn_platform_access_recording`/`transcript` both hardcode `'SENSITIVE_MEDIA_ACCESS'`) — the required purpose is never client-suppliable, closing the class of bug where a caller could request check against a purpose different from what the action actually needs.

## 16. Organization Suspend / Reactivate

`organization.fn_platform_suspend_organization(p_organization_id UUID, p_admin_user_id UUID, p_reason TEXT) RETURNS TEXT` — `SECURITY DEFINER`, `app_platform_admin`-only (`app_api` revoked). Validates caller via `is_platform_admin()`, `p_reason` length `[10,2000]`; locks the org row (`FOR UPDATE`); idempotent no-op if already `SUSPENDED`; raises if `CANCELLED` (terminal); otherwise sets `status='SUSPENDED'` and atomically audits `ORGANIZATION_SUSPENDED` with `{previous_status, reason}`.

`organization.fn_platform_reactivate_organization(p_organization_id UUID, p_admin_user_id UUID, p_reason TEXT) RETURNS TEXT` — mirror image, `ORGANIZATION_REACTIVATED`.

**Endpoints:** `POST /api/v1/platform-admin/organizations/{organization_id}/suspend`, `POST /api/v1/platform-admin/organizations/{organization_id}/reactivate`. Neither requires a break-glass grant (org-lifecycle actions are metadata-level, not content-level) — this is an explicit, narrower trust boundary than sensitive-media access, consistent with `SUPPORT_ORG_LIFECYCLE` existing as a *break-glass purpose* for other flows that do combine org-lifecycle context with content access, without making suspend/reactivate itself break-glass-gated.

## 17. `is_platform_admin()` Hardening History

```sql
-- 107_5B5, current definition:
CREATE OR REPLACE FUNCTION organization.is_platform_admin()
RETURNS BOOLEAN LANGUAGE sql STABLE SECURITY INVOKER AS $$
  SELECT session_user = 'app_platform_admin'
     AND COALESCE(current_setting('app.is_platform_admin', true), 'false') = 'true'
$$;
```

- **001_5B (original):** trusted only `current_setting('app.is_platform_admin', true) = 'true'` — a session-local GUC any `app_api` session could self-set via `SET`/`set_config()`. Self-forgeable.
- **106_5H3 (fix 1 — NULL fail-open):** the original had a code path where an unset GUC (`NULL`) could evaluate truthy in some call sites; `106_5H3` wraps the read in `COALESCE(..., 'false')` so an unset GUC is unambiguously `FALSE`.
- **107_5B5 (fix 2 — self-forgery):** adds the `session_user = 'app_platform_admin'` conjunct. This is the actual trust boundary — the GUC alone was never sufficient once this shipped, because `session_user` is fixed at connection time by the authenticated credential and cannot be altered by SQL running inside the session. `current_user` was deliberately **not** used for this check: `current_user` changes to the owning role inside a `SECURITY DEFINER` function body, so binding to `current_user` would make the check tautologically true for every `SECURITY DEFINER` function owned by `app_platform_admin`, regardless of who actually connected. `session_user` is immune to this. The function remains `PUBLIC`-executable (safe, since forging `session_user` is not possible from SQL).
- **108_5B6:** does not touch `is_platform_admin()` at all — its finding (F-26-1) is a table-ACL propagation defect on a different object (`voice.transcript_segments`'s partitions), not an identity-check defect. See §21.5.

## 19. Refund Saga — Design

Three strictly separated steps, no PostgreSQL transaction held across network I/O:

1. **Reservation** (`app_platform_admin`, transaction 1, commits): `billing.fn_platform_reserve_refund(p_organization_id UUID, p_admin_user_id UUID, p_payment_attempt_id UUID, p_amount NUMERIC(18,4), p_currency CHAR(3), p_reason TEXT) RETURNS UUID`. Validates the payment attempt, checks already-refunded amount, inserts a `PENDING` `billing.refunds` row, commits. This is the **only** refund action a Platform Admin (human or `app_platform_admin` DB session) can perform.
2. **Provider call** (application layer, outside any DB transaction): the trusted backend calls `PaymentProviderPort.refund(...)` using the reservation's amount/currency/reference. No DB transaction is open during this call.
3. **Settlement** (`app_billing_reconciler` only, transaction 2): based on the provider's verified response, exactly one of:
   - `billing.fn_platform_settle_refund(p_refund_id UUID, p_admin_user_id UUID, p_provider_refund_id TEXT) RETURNS TEXT` — `IF session_user <> 'app_billing_reconciler' THEN RAISE EXCEPTION`. Idempotent no-op if already `SUCCEEDED`; raises if already `FAILED` (terminal). Sets `status='SUCCEEDED'`, `provider_refund_id`, `completed_at`; atomically audits `REFUND_SETTLED` (`actor_type='WORKER'`, `actor_ref='app_billing_reconciler'`, `resource_snapshot={provider_refund_id, requested_by_admin_user_id}`).
   - `billing.fn_platform_fail_refund(p_refund_id UUID, p_admin_user_id UUID, p_failure_reason TEXT) RETURNS TEXT` — same `session_user` guard; idempotent no-op if already `FAILED`; raises if already `SUCCEEDED` (terminal); audits `REFUND_FAILED`.

**A human Platform Admin or an `app_platform_admin` DB connection cannot call either settlement function — `EXECUTE` is revoked from both `app_api` and `app_platform_admin`, granted only to `app_billing_reconciler`.** `app_billing_reconciler` itself is a `LOGIN` role with no direct table privileges on any billing table and no `BYPASSRLS` — its only capability is these two `EXECUTE` grants, following the same minimal-principal pattern as `app_voice_reconciler` (`099_5C1.sql`).

**Idempotency / retry:** provider timeout after the call is issued but before a response is confirmed leaves the refund `PENDING`; the reconciliation worker's own retry/reconciliation loop (poll the provider by the reservation's idempotency key, or process the provider's own webhook) is what eventually drives exactly one of settle/fail — this document does not re-specify that worker's retry policy, which is a 6K/backend-implementation concern, not a new DB contract.

**Endpoint:** `POST /api/v1/platform-admin/organizations/{organization_id}/refunds` (reserve only). There is intentionally no `POST /api/v1/platform-admin/refunds/{refund_id}/settle` or `.../fail` endpoint on the Platform Admin surface — settlement is not a Platform Admin action at all, so no such endpoint should ever be built here.

## 21. Sensitive Media Support

### 21.1 Recording

`voice.fn_platform_access_recording(p_grant_id UUID, p_admin_user_id UUID, p_organization_id UUID, p_session_id TEXT, p_recording_id UUID) RETURNS TABLE(id, call_id, conversation_id, storage_ref, storage_provider, content_type)` — `SECURITY DEFINER`. Checks, in order: `session_user = 'app_platform_admin'` (raises otherwise); `fn_break_glass_check(..., 'SENSITIVE_MEDIA_ACCESS')` (raises if false); recording exists for the given organization (raises otherwise). On success, atomically audits `RECORDING_ACCESS_GRANTED` (`resource_snapshot = {grant_id, call_id, recording_id}` — never the storage bytes) then returns the row, including `storage_ref` (the caller — the trusted backend — is then responsible for generating a short-lived signed URL/stream from `storage_ref`; this function does not itself stream bytes).

### 21.2 Transcript

`voice.fn_platform_access_transcript(p_grant_id UUID, p_admin_user_id UUID, p_organization_id UUID, p_session_id TEXT, p_transcript_id UUID) RETURNS TABLE(sequence_number, speaker, text, is_partial, start_ms, end_ms, language)` — identical guard structure to §21.1 (same `session_user` check, same `SENSITIVE_MEDIA_ACCESS` break-glass check, same ownership cross-check). On success, atomically audits `TRANSCRIPT_ACCESS_GRANTED` (`resource_snapshot = {grant_id, call_id, transcript_id}` — **never the transcript text itself**) then returns the ordered segment rows (`transcript_segments`, joined by `transcript_id`/`organization_id`, `ORDER BY sequence_number`).

### 21.5 F-26-1 — Child-Partition ACL Bypass (History, closed by `108_5B6`)

Surfaced during this same freeze-gate review's own re-verification of `107_5B5`'s sensitive-media fix — not by an external report. `107_5B5`'s `REVOKE ALL ON voice.transcript_segments FROM app_platform_admin` plus its column-restricted `GRANT SELECT` named only the **parent** relation of a `RANGE (created_at)`-partitioned table (`014_5C.sql`). PostgreSQL binds privilege checks to the exact relation named in a query and does not propagate a parent-level `REVOKE`/`GRANT` to already-existing child partitions — each partition keeps its own independent ACL. `transcript_segments`'s five partitions (`_2026_09`/`_10`/`_11`/`_12`/`_default`) had retained `018_5C.sql`'s original unrestricted `DELETE, INSERT, SELECT, UPDATE` grant to `app_platform_admin`, live-confirmed exploitable: `SELECT text FROM voice.transcript_segments` (parent) correctly denied, but the identical query against `voice.transcript_segments_2026_09` (naming the child directly) succeeded, as did an unrestricted `DELETE`.

This is the same defect class already fixed twice before in this codebase against a different partitioned table (`workflow.workflow_executions` — `076_5K1.sql` FIX 2, `100_5G1.sql`'s defensive per-partition loop) — F-26-1 was a recurrence of a known pattern in a table those earlier fixes didn't cover, not a novel class of bug.

`108_5B6.sql` fix: a `DO $$...$$` block walks `pg_inherits` for `voice.transcript_segments`'s current children and applies the identical `REVOKE ALL` + column-restricted `GRANT SELECT` (restricted column list, §21.6) already applied to the parent; a second, self-verifying `DO $$...$$` block asserts via `has_table_privilege`/`has_column_privilege` that no partition retains any table-level `SELECT`/`INSERT`/`UPDATE`/`DELETE`, that metadata (`sequence_number`) `SELECT` is retained, and that column-level `SELECT` on `text` is absent — raising if violated, so the fix cannot silently regress. Live-validated on both fresh and incremental chains (`MIGRATION_MANIFEST.md` Row 108): 8 `ERROR: permission denied` results across the proof-of-fix battery (1 parent + 3 for `_2026_09` + 4 for the other four partitions), matching expectation exactly. A follow-up 21-table partitioned-privilege spot-check confirmed F-26-1 was isolated to this one table, not a wider unaddressed pattern (`audit.audit_events` and `workflow.workflow_executions`, the platform's other two restricted-and-partitioned tables, were independently re-confirmed clean).

`voice.fn_platform_access_transcript` itself is unchanged by `108_5B6` and remains the sole guarded path to segment text.

## 27.1 Application-Layer Principal Authorization Matrix (new this pass — §12)

The table above governs the PostgreSQL session-level trust boundary (which DB role may execute which function or touch which table) and is necessary but not sufficient: it says nothing about which *application-layer* caller identity is allowed to reach a given Platform Admin endpoint in the first place, since every row in §27 is exercised only through the single `app_platform_admin` DB session regardless of which human/API-key principal initiated the HTTP request. This subsection adds that missing layer.

| Application-layer principal | Can call Platform Admin endpoints? | Notes |
|---|---|---|
| Platform Admin human operator (6B `platform_admin` role claim on session) | ✓, all endpoints in §25 | The only principal this document's endpoints are designed for; every §25 row assumes this caller |
| Tenant-scoped human user (any 6B org-scoped role, incl. tenant-side `org_admin`) | ✗, unconditionally | No tenant role, however privileged within its own organization, may reach `/api/v1/platform-admin/*`; enforced at the application-router layer before any DB call is made, independent of and in addition to the DB-level `session_user`/GUC check (§17, `organization.is_platform_admin()`) |
| Tenant-scoped API key (6B API-key auth) | ✗, unconditionally | Same as above — API keys are always tenant-scoped in this system; there is no Platform-Admin-scoped API key concept |
| `app_worker` / background job identity (no human principal) | ✗ for all `/api/v1/platform-admin/*` HTTP routes (n/a — workers do not call HTTP endpoints); ✓ at the DB layer only for the specific functions §27 lists as worker-reachable | Clarifies that the DB-level `app_worker` row in §27 is about direct DB access from worker processes, not about workers being able to invoke Platform Admin REST endpoints, which they never do |
| `app_billing_reconciler` identity | ✗ for all `/api/v1/platform-admin/*` HTTP routes (n/a) | Same clarification — reconciler is a DB-only, LOGIN-only principal (§10's Actor Model), never an HTTP caller |
| Break-glass grant holder without the `platform_admin` role claim | ✗ | Break-glass is an additional, narrower gate layered on top of the Platform Admin role for a specific subset of actions (§17); it is never a substitute for the role claim itself and never independently authorizes reaching an endpoint |

## 32. Caching

## 33. Resilience / Idempotency

- Break-glass grant issuance: not idempotent by design (each call issues a new grant); the client-supplied idempotency-key header still applies to prevent double-submission from a retried HTTP request.
- Org suspend/reactivate, refund settle/fail: DB-level idempotent no-ops on repeat calls in the same terminal-adjacent state (see respective function descriptions).
- Refund saga overall: see §19's idempotency/retry discussion — no PostgreSQL transaction is ever held across the provider network call.

## 56. F-26-1 Operational Runbook (required by `108_5B6.sql`'s own header)

## 62. Plan / PlanVersion / PlanPrice Administration (new this pass — §3, `DBGAP-6M-06`)

**Scope and ownership.** `billing.plans`, `billing.plan_versions`, and `billing.plan_prices` (`047_5H.sql`) are the catalog tables backing every tenant's subscription. No phase before this one designed a Platform Admin write surface for them; 6C and other tenant-facing phases only ever *read* the currently-published plan/version/price for a tenant's own subscription flow. This section closes that gap. It does not touch or re-scope any tenant-facing read endpoint.

**Lifecycle model — corrected against the real `047_5H.sql` DDL (this pass; an earlier draft of this section described a `status` enum with `DRAFT`/`PUBLISHED`/`RETIRED` values and per-price `currency`/`billing_interval` fields that do not exist in the schema — fixed here per §17).** A `Plan` (`id`, `name` UNIQUE, `description`, `is_active`) is a stable named product (e.g. "Growth"); `is_active = FALSE` deactivates the whole product for new subscriptions. Deactivation is a one-way idempotent state flip via `billing.fn_platform_deactivate_plan` (§65) — it never deletes the `Plan` row or any of its versions/prices, existing subscriptions on the plan are unaffected, and calling it again on an already-inactive plan is a harmless no-op that still records its own audit event (there is no corresponding reactivate path; a plan is brought back by creating a new one). Each `Plan` has one or more `PlanVersion` rows (`billing_cycle` — `MONTHLY`/`ANNUAL` — `base_price_amount`, `base_price_currency`, `effective_from`, `is_published` BOOLEAN default `FALSE`). There is no `RETIRED` state at the DB layer: a version starts `is_published = FALSE` ("draft" in API terms) and may transition exactly once to `is_published = TRUE` ("published"); `billing.fn_plan_version_immutability()` (`047_5H.sql`) then locks `base_price_amount`/`base_price_currency`/`billing_cycle`/`effective_from` forever. A mistake is corrected by creating and publishing a new version, not by mutating or un-publishing a published one; superseding an older published version is a plan-level convention (the newest published version is "current"), not a DB-enforced state transition. Each `PlanVersion` has one or more `PlanPrice` rows (`metric` UNIQUE per version, `unit_label`, `included_quantity`, nullable `overage_rate_amount`/`overage_rate_currency`) representing the version's metered usage components — one row per billable metric (e.g. "minutes", "seats"), not per currency/interval (currency and billing cadence are fixed once, at the parent `PlanVersion`). `PlanPrice` rows may only be created while the parent version is unpublished.

### 66.1 Owner decision `FAR-OD-02` — two layers, never one

| Layer | Object | Owner | Lifetime | Written by |
|---|---|---|---|---|
| **Commercial / base quota** | `billing.quota_configs` (`052_5H.sql`) | Plan provisioning / subscription lifecycle | Until the commercial agreement changes | `app_worker`, `app_platform_admin` (pre-existing grants, unchanged by `111_5H4`) |
| **Temporary platform-admin override** | `billing.quota_overrides` (`111_5H4`, new, additive) | Platform Admin | `effective_from` → `expires_at`, or until superseded | `billing.fn_platform_set_quota_override()` **only** — no role holds `INSERT`/`UPDATE`/`DELETE` on the table |

The override layer is **additive**. `billing.quota_configs` is not dropped, not re-keyed, and not written by the override path in any form. `106_5H3`'s `quota_configs.override_reason` / override-era columns are left in place; they are simply no longer the mechanism.

The defect this closes (`FAR-P1-05`): `billing.quota_configs` carries `UNIQUE (organization_id, metric)`, so a single row per `(org, metric)`. The `107_5B5`-era override mutated that one row. When the override expired, the only effective `hard_limit` for the metric disappeared with it, and every consumer read "no row found" as **unlimited** — a quota override expiring into *no quota at all*. Under Option B the base row is never touched, so expiry falls back to whatever the base says **at that moment**.

### 66.2 `POST /api/v1/platform-admin/organizations/{organization_id}/quota-overrides` — write path

Route, method, permission and audit `action_kind` are **unchanged**. The function signature is unchanged:

```
billing.fn_platform_set_quota_override(
  p_organization_id UUID, p_admin_user_id UUID, p_metric TEXT,
  p_soft_limit NUMERIC, p_hard_limit NUMERIC, p_reason TEXT,
  p_expires_at TIMESTAMPTZ DEFAULT NULL, p_unit_label TEXT DEFAULT NULL
) RETURNS UUID   -- SECURITY DEFINER, SET search_path = billing, organization, pg_catalog
```

What changed is the body. In order, the function now: (1) asserts `organization.is_platform_admin()`; (2) requires `p_organization_id`; (3) requires `p_admin_user_id` (restored from `106_5H3` — an unattributed override must not be creatable); (4) validates `p_metric` against the canonical vocabulary (§66.4); (5) requires `p_reason` of 10–2000 characters; (6) requires `p_expires_at` to be `NULL` (permanent-until-superseded) or strictly in the future; (7) validates `soft_limit >= 0`, `hard_limit >= 0`, `soft_limit <= hard_limit`, with `NULL` `hard_limit` meaning **unlimited** and fractional `NUMERIC(18,4)` values accepted as stored; (8) asserts the organization exists (preserved from `107_5B5`); (9) derives the canonical `unit_label` unless the caller supplies one; (10) takes `pg_advisory_xact_lock(hashtext('billing.quota_override:' || org || ':' || metric))`; (11) `UPDATE`s the previously-current row to `superseded_at = NOW()`; (12) `INSERT`s the new override row; (13) writes the `QUOTA_OVERRIDE_SET` audit event via `audit.fn_insert_audit_event()` **in the same transaction** — if the audit write fails, the override is not created.

Supersession is atomic and one-directional. A superseded row is retained, never deleted, and can never become current again: the partial unique index `uq_qo_org_metric_current ON billing.quota_overrides (organization_id, metric) WHERE superseded_at IS NULL` is the structural backstop behind the advisory lock, so a check-then-insert race cannot produce two current rows (it raises `23505 / uq_qo_org_metric_current` instead).

**`billing.quota_configs` is not written at step 12 or anywhere else in this function.** That is the whole of `FAR-OD-02`.

Privileges on the table are deliberately narrower than `quota_configs`: `REVOKE ALL ... FROM PUBLIC`, then `GRANT SELECT` to `app_api, app_worker, app_readonly, app_platform_admin`. Platform Admin does not receive raw DML here — every mutation must carry a validated reason, a validated admin identity and an atomic audit event, which only the guarded function guarantees. `EXECUTE` on the function is revoked from `PUBLIC` and from `app_api`, and granted to `app_platform_admin` only.

### 66.3 `GET /api/v1/platform-admin/organizations/{organization_id}/quota-overrides` — read model

The §18 statement that `app_platform_admin` lists overrides via direct `SELECT` on `billing.quota_configs` is superseded. **An override is not a base row**, and the listing must not conflate them. The listing reads `billing.quota_overrides`, via `GRANT SELECT ON billing.quota_overrides TO ... app_platform_admin` and the `rls_qo_platform_admin` policy (`FOR ALL USING (organization.is_platform_admin())` — which, under `FORCE ROW LEVEL SECURITY`, is also what lets the `SECURITY DEFINER` writer satisfy its `WITH CHECK`). No new grant, no new role, no `BYPASSRLS`.

Every row's state is **derived at read time** from two stored timestamps against `NOW()`; there is no stored status column to drift:

| Reported state | Derivation | Meaning |
|---|---|---|
| **ACTIVE** | `superseded_at IS NULL AND effective_from <= NOW() AND (expires_at IS NULL OR expires_at > NOW())` | This override is what the resolver is returning right now. At most one per `(organization_id, metric)`, enforced by `uq_qo_org_metric_current`. |
| **EXPIRED** | `superseded_at IS NULL AND expires_at IS NOT NULL AND expires_at <= NOW()` | Time ran out. Nothing was mutated at expiry — the row is untouched and the resolver has simply stopped selecting it. The tenant is back on the **current** base quota. |
| **SUPERSEDED** | `superseded_at IS NOT NULL` | Replaced by a later override for the same `(organization_id, metric)`. Retained for audit; can never become current again. |

A row whose `expires_at` has passed **and** which was later superseded reports **SUPERSEDED** — `superseded_at` is evaluated first, because it is the terminal, irreversible state.

Expiry is a read-time predicate, not a job: no sweeper, no scheduled task, nothing to fall behind. `NOW()` is `transaction_timestamp()`, so an override's effective state is stable within a transaction and a crossing of `expires_at` becomes visible to the **next** transaction.

Available columns for the listing: `id, organization_id, metric, soft_limit, hard_limit, unit_label, reason, effective_from, expires_at, superseded_at, created_by, created_at`. `created_by` is the `p_admin_user_id` that was validated `NOT NULL` at write time (logical reference to `identity.users.id`; no cross-schema FK, per the 5A convention), so every listed override is attributable.

### 66.4 Canonical metric vocabulary — the `FR-TEN-005` correction

`p_metric` is **not** free text. It is checked twice, independently:

1. `billing.fn_is_canonical_usage_metric(TEXT)` inside `fn_platform_set_quota_override()` — a rejected metric raises `P0001`, so the API surfaces a validation error rather than silently storing a typo;
2. `CONSTRAINT chk_qo_metric_canonical CHECK (billing.fn_is_canonical_usage_metric(metric))` on the table itself — a `23514` violation, which holds even if some future path tries to write the table another way.

The canonical vocabulary is 5H §11.1's 15 usage dimensions: `CALL_MINUTES`, `AI_MINUTES`, `STT_SECONDS`, `TTS_CHARACTERS`, `LLM_PROMPT_TOKENS`, `LLM_COMPLETION_TOKENS`, `EMBEDDING_TOKENS`, `CAMPAIGN_CALLS`, `WORKFLOW_EXECUTIONS`, `TOOL_EXECUTIONS`, `KNOWLEDGE_RETRIEVALS`, `STORAGE_GB`, `API_REQUESTS`, `ACTIVE_AGENTS`, `ACTIVE_PHONE_NUMBERS`.

`AGENT_COUNT` — the metric name used by the `107_5B5` override path — is **rejected, not aliased**. It was never a member of the canonical vocabulary, and silently mapping it to `ACTIVE_AGENTS` would hide the fact that the two paths had drifted apart (`FAR-P1-04`). Any caller still sending `AGENT_COUNT` gets a loud validation failure and must be corrected.

`billing.fn_resolve_effective_quota()` applies the same check and raises on a non-canonical metric for the same reason: returning zero rows for a typo would be read by every consumer as "no quota configured", i.e. unlimited — the worst possible reading of a misspelling.

**Disclosed gap, unchanged by this pass.** `billing.quota_configs.metric` is unconstrained `TEXT` (`052_5H.sql` has no metric `CHECK`), so a base row can carry any string; the override layer cannot. Concretely, "concurrent calls" — named in `FR-TEN-005`'s requirement text and referenced by 6H §21 as `CONCURRENT_CALLS` — has **no** canonical metric and no seeding migration, and is therefore not representable as a quota override. It is a concurrency ceiling, not a metered usage dimension. `FR-TEN-005` remains **COVERED** for the four dimensions it enumerates that *are* metered (`ACTIVE_AGENTS`, `ACTIVE_PHONE_NUMBERS`, `STORAGE_GB`, `API_REQUESTS`); the concurrency ceiling is recorded here as a known limitation of the override surface rather than papered over by relaxing the vocabulary.

### 66.5 Effective-quota resolution — what consumers read

Platform Admin diagnostics, 6K reporting (§53) and 6E admission (§43.12) all resolve through one function, `billing.fn_resolve_effective_quota(p_organization_id UUID, p_metric TEXT)`, which returns `(metric, soft_limit, hard_limit, unit_label, source, override_id, effective_from, expires_at)` where `source` is `'PLATFORM_OVERRIDE'` or `'BASE'`:

1. the currently-effective, non-superseded override for `(organization_id, metric)`, if one exists; **else**
2. the **current** `billing.quota_configs` row, read live with no effective-window filter; **else**
3. no row — which the consumer interprets per its own contract, and which is now reachable only when no quota was ever configured, not as a side effect of an override expiring.

It is `STABLE` and **`SECURITY INVOKER`**, not `SECURITY DEFINER`: a tenant consumer resolves its own effective quota under its own privileges and its own RLS, and does not borrow Platform Admin rights to do so. A non-Platform-Admin caller whose `app.tenant_id` is unset, or does not match `p_organization_id`, is refused. Tenant isolation is preserved on the read path exactly as on the write path.

Because the base row is read live at step 2, a base value changed while an override is active is the value that takes over at expiry — base `10`, override `20`, base edited to `12` mid-flight yields `20` while the override is active and `12` after it expires. No historical base value is copied into the override row, and none is fabricated.

### 66.6 What did **not** change

- **No new route, no new method, no new permission, no new error code.** Both quota-override endpoints keep their paths, their `app_platform_admin`-only gating and their existing error mapping. Every validation failure enumerated in §66.2 raises `P0001` and maps to the **existing** §28 code `QUOTA_OVERRIDE_VALIDATION_FAILED` (422) — no new code is added, and none is renamed. A second-current-override race loses to `uq_qo_org_metric_current` (`23505`) and a non-canonical metric that somehow reaches the table loses to `chk_qo_metric_canonical` (`23514`); both are server-side invariant violations rather than new client-facing conditions, so both surface as the same 422. A missing `EXECUTE` privilege raises `42501` and maps to the existing `403` (`PLATFORM_ADMIN_REQUIRED`). The §28 row's caveat that the accepted-value range was "not reconfirmed this pass" is closed by §66.2 and §66.4, which enumerate it exactly.
- **Audit unchanged in shape and literal:** `action_kind = 'QUOTA_OVERRIDE_SET'`, `actor_type = 'PLATFORM_ADMIN'`, `resource_type = 'QUOTA_OVERRIDE'`, `resource_id = <new override id>`, written in the same transaction as the supersede+insert pair. This is the same atomicity property §65's closing paragraph records for the `107_5B5` family of functions.
- **`110_5C2` was not amended.** 6E's `voice.fn_assert_agent_quota_admission(UUID)` was re-pointed at the resolver by a `CREATE OR REPLACE` **in `111_5H4`**, with an identical signature, security class and ACL; every `110_5C2` invariant (the counted-set definition, the mutation-guard trigger, the `created_by` trust boundary, the fractional-limit admission arithmetic) is preserved. See 6E §43.12.
- **Redis is unchanged.** No key, TTL or invalidation contract is altered; only the source a cache entry is *seeded* from changes. See 6K §53.4.
- **No quota-override endpoint gains a delete or edit verb.** An override is corrected by issuing a new one, which supersedes it — the same immutability discipline as `billing.plan_versions` (§65.3).
