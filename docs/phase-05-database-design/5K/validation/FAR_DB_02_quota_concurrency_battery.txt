§2 - FRACTIONAL HARD-LIMIT BATTERY (FAR-P1-02)
==================================================================================
  billing.quota_configs.hard_limit is NUMERIC(18,4) and structurally permits
  fractional values, so the pre-amendment test `v_active >= v_hard_limit` was
  mathematically wrong: with hard_limit = 1.5000 and v_active = 1, 1 >= 1.5 is
  false, the INSERT succeeded, and the COMMITTED count became 2 > 1.5. The amended
  admission asserts the post-insert invariant (v_active + 1) <= v_hard_limit and
  rejects exactly its negation. The configured commercial limit is compared as
  stored - never rounded, CEIL-ed or FLOOR-ed.

  Each case below sets the limit, prefills the counted set, then performs ONE real
  guarded call and re-reads the COMMITTED count. `limit_respected` is the machine
  check `active_after <= hard_limit`.

   CASE A | hard_limit=1.5000 | active_before=0 | ACCEPTED id=01a0a3a9-f270-7132-9f73-732775211578 | active_after=1 | limit_respected=t | PASS
   CASE B | hard_limit=1.5000 | active_before=1 | REJECTED sqlstate=53400 msg=ACTIVE_AGENTS quota exceeded | active_after=1 | limit_respected=t | PASS
   CASE C | hard_limit=0.5000 | active_before=0 | REJECTED sqlstate=53400 msg=ACTIVE_AGENTS quota exceeded | active_after=0 | limit_respected=t | PASS
   CASE D | hard_limit=2.0000 | active_before=1 | ACCEPTED id=01a0a3a9-f273-781a-9e01-01f0ec324226 | active_after=2 | limit_respected=t | PASS
   CASE E | hard_limit=2.0000 | active_before=2 | REJECTED sqlstate=53400 msg=ACTIVE_AGENTS quota exceeded | active_after=2 | limit_respected=t | PASS
   CASE F (clone) | hard_limit=1.5000 | active_before=1 | REJECTED sqlstate=53400 msg=ACTIVE_AGENTS quota exceeded | active_after=1 | limit_respected=t | PASS
   CASE G (clone) | hard_limit=2.0000 | active_before=1 | ACCEPTED id=01a0a3a9-f275-7862-b8c6-c643f5ab010f | active_after=2 | limit_respected=t | PASS
   CASE H (no quota row)    | ACCEPTED id=01a0a3a9-f276-724e-82d7-d74eb7227958 | active_after=1 | PASS
   CASE I (hard_limit NULL) | ACCEPTED id=01a0a3a9-f276-7ed7-862e-2e71b00810bc | active_after=1 | PASS

   GLOBAL INVARIANT PASS: no organization has committed ACTIVE_AGENTS > hard_limit

  Reading of the results:
    A/B are the directive's critical boundary: at limit 1.5000 the FIRST agent is
      admitted (1 <= 1.5) and the SECOND is refused (2 > 1.5). Under the old
      condition B would have been ACCEPTED, committing 2 against a limit of 1.5.
    C proves a limit below 1 admits nothing at all (1 > 0.5), rather than admitting
      one agent as the old `0 >= 0.5 is false` path did.
    D/E confirm the integer case is unchanged: 2.0000 admits exactly two.
    F/G apply the same boundary to POST /agents/{id}/clone, which shares the same
      admission function.
    H/I confirm absent quota row and NULL hard_limit remain unmetered - the
      amendment narrows nothing that was previously permitted.

§11/§13 - TWO TRULY CONCURRENT ADMISSIONS (cases A, B, E, K, L)
==================================================================================
HOW GENUINE CONCURRENCY WAS PRODUCED (the directive forbids simulating it sequentially)
----------------------------------------------------------------------------------
  A controller session first takes the SAME advisory key the guarded function uses:

     BEGIN;
     SELECT pg_advisory_xact_lock(hashtext('voice.agent_quota:<org>')::bigint);

  Two worker psql PROCESSES are then launched in parallel. Each enters
  voice.fn_create_agent() / voice.fn_clone_agent(), reaches the internal
  pg_advisory_xact_lock() and BLOCKS. The harness polls pg_locks until it observes

     SELECT count(*) FROM pg_locks
      WHERE locktype='advisory' AND NOT granted
        AND objid = (hashtext('voice.agent_quota:<org>')::bigint & 4294967295);

  reaching 2 - i.e. both workers are simultaneously parked on the lock, INSIDE the
  function, before either has counted anything. Only then does the controller
  COMMIT, releasing the key and letting the two workers race for it. The "workers
  simultaneously blocked" line in each case below is that observation, and it is
  what distinguishes this from sequential execution.
