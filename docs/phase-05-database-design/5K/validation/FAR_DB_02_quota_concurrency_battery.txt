HOW GENUINE CONCURRENCY WAS PRODUCED (§13 forbids simulating it sequentially)
----------------------------------------------------------------------------------
  A controller session first takes the SAME advisory key the guarded function uses:

     BEGIN;
     SELECT pg_advisory_xact_lock(hashtext('voice.agent_quota:<org>')::bigint);

  Two worker psql processes are then launched in parallel. Each enters
  voice.fn_create_agent() / voice.fn_clone_agent(), reaches the internal
  pg_advisory_xact_lock() and BLOCKS. The harness polls pg_locks until it observes

     SELECT count(*) FROM pg_locks
      WHERE locktype='advisory' AND NOT granted
        AND objid = (hashtext('voice.agent_quota:<org>')::bigint & 4294967295);

  reaching 2 - i.e. both workers are simultaneously parked on the lock, inside the
  function, before either has counted anything. Only then does the controller COMMIT,
  releasing the key and letting the two workers race for it. The "workers
  simultaneously blocked" line in each case below is that observation.

      SELECT voice.fn_create_agent(...)            -- quota-guarded sole INSERT path
      SELECT audit.fn_insert_audit_event(...)      -- existing audit mechanism (5B)

  READ-THIS ANNOTATION FOR CASE 15b (cosmetic harness artifact, not a defect):
  ------------------------------------------------------------------------------
  In 15b the quota rejection aborts the transaction at the FIRST statement. The psql
  variable :agent_id is therefore never assigned by \gset, so the two following
  statements in the same script are sent with an unsubstituted ":" and psql reports
  `syntax error at or near ":"`. Those two errors are psql-client artifacts of the
  test script, NOT database behaviour: the transaction was already in an aborted
  state and would have discarded both writes regardless. The transaction ended in
  ROLLBACK and the three counts stayed at 2 / 2 / 2, which is the assertion under
  test. A reviewer should not read those two lines as a failure.

  §15 verdict: the Agent row, the AGENT_CREATED audit event and the `agent.created`
  outbox row commit together (1/1/1), roll back together (still 1/1/1, then 2/2/2 on
  retry), and a quota rejection produces NONE of the three. Rejection happens before
  the INSERT, so no Agent-created audit event or domain event is ever emitted for a
  rejected create. Migration 110 introduces no second event mechanism; it emits nothing
  at all - the existing 5B audit function and 5B transactional outbox are unchanged.
