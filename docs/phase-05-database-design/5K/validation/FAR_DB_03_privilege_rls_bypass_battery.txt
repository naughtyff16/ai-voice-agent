PART 2 - §13 H / §14: RAW INSERT ATTEMPTED AS EVERY RUNTIME ROLE
==================================================================================
  Each role was made to attempt a direct `INSERT INTO voice.agents ...` naming its
  row 'bypass-<role>', with tenant context correctly set - i.e. the most favourable
  possible conditions for a bypass.

   app_api                        ERROR:  permission denied for table agents
   app_worker                     ERROR:  permission denied for table agents
   app_platform_admin             ERROR:  permission denied for table agents
   app_readonly                   ERROR:  permission denied for table agents
   app_voice_reconciler           ERROR:  permission denied for table agents
   app_billing_webhook_ingress    ERROR:  permission denied for schema voice
   app_billing_reconciler         ERROR:  permission denied for schema voice
rows named bypass-% actually committed: 0   EXPECT 0

  Not one runtime role can insert an Agent row by any path other than the two
  guarded functions. Note the two distinct denial modes, both fatal to a bypass:
    - permission denied for table agents ..... the role can reach schema voice but
      110 revoked its INSERT (app_api, app_worker, app_platform_admin, app_readonly,
      app_voice_reconciler)
    - permission denied for schema voice .... the billing roles never had access to
      the voice schema at all (app_billing_webhook_ingress, app_billing_reconciler)

  app_migration is the eighth role. It holds BYPASSRLS but has_table_privilege(
  'app_migration','voice.agents','INSERT') = f, shown in Part 1 §4. BYPASSRLS skips
  row-level policies; it does NOT skip table-level ACLs. This is exactly why the
  REVOKE binds even the two privileged roles.

  NO ROLE RETAINS RAW INSERT. There is therefore no role for which the directive's
  fallback ("if any role must retain raw INSERT, document exactly why and prove it
  cannot bypass the quota invariant") applies - the stronger outcome was achievable
  and was taken.

==================================================================================
PART 3 - WHY THE QUOTA INVARIANT IS STRUCTURALLY ENFORCEABLE, NOT MERELY ADVISORY
==================================================================================
  1. voice.agents INSERT is revoked from every runtime role (Part 1 §4, Part 2).
  2. The only remaining INSERT paths are voice.fn_create_agent() and
     voice.fn_clone_agent(), both SECURITY DEFINER owned by postgres (Part 1 §1).
  3. Both call voice.fn_assert_agent_quota_admission() BEFORE their INSERT
     (CONTEXT traces in FAR_DB_02 show fn_create_agent line 22 / fn_clone_agent
     line 55 -> fn_assert_agent_quota_admission line 57 at RAISE).
  4. The assertion function is reachable by NOBODY directly: has_function_privilege
     = f for all eight app roles and for PUBLIC (Part 1 §2, §3). It executes only as a
     nested call inside the two definer functions, so no principal can call it to
     "pre-book" a slot, and no principal can skip it.
  5. The advisory lock is taken INSIDE the assertion function, inside the caller's
     transaction. The API layer issues no lock statement of its own, which is what
     restores compliance with frozen 6A §17.3.

  Therefore: to create an Agent, a caller MUST pass the quota guard. That is the
  difference between "an enforcement primitive exists" and "a compliant enforcement
  path is the only path" - the distinction DB-BLOCKER-FINAL-API-001 was raised over.
