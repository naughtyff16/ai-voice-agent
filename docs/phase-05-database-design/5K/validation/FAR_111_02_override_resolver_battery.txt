TIME SEMANTICS
  NOW() inside these functions is transaction_timestamp(). The effective quota is
  therefore STABLE for the duration of a transaction, and an override that
  expires mid-transaction becomes visible as expired to the NEXT transaction.
  This is the intended read-time expiry semantic: expiry is evaluated when the
  quota is read, and no background job, sweeper or cron is required to retire an
  expired override.

PART 2 - BATTERY B: EFFECTIVE-QUOTA RESOLUTION (FAR-OD-02 / FAR-P1-05)
==================================================================================

The contract under test (FAR-OD-02 Option B):

  Layer 1  COMMERCIAL / BASE QUOTA        billing.quota_configs
  Layer 2  TEMPORARY PLATFORM OVERRIDE    billing.quota_overrides

  Resolution = the active, non-superseded override IF one exists,
               ELSE the CURRENT commercial baseline.
  The override NEVER overwrites the baseline. On expiry the effective quota
  falls back to the CURRENT baseline - not to unlimited, and not to a stale
  historical baseline value.

-- B.PRE the resolver is entered through its TENANT path, not its admin path

              tenant_ctx              | is_platform_admin
   -----------------------------------+-------------------
    11111111-1111-7111-a111-00000000000a | f

  app.tenant_id is set to FAR Org A and organization.is_platform_admin() reads
  f, so every resolver call below is evaluated under the tenant branch. (The
  fixture DELETE/UPDATE/INSERT statements around them are superuser harness
  setup - see the CALLER note above.)

CASE B1 - base present, no override
    metric    | soft_limit | hard_limit | unit_label | source | override_id
  ------------+------------+------------+------------+--------+-------------
   CALL_MINUTES|  800.0000 |  1000.0000 | minutes    | BASE   |
  => source=BASE, hard_limit=1000. PASS.

CASE B2 - active temporary override (hard 2000, expires +7d)
   CALL_MINUTES| 1600.0000 |  2000.0000 | minutes    | PLATFORM_OVERRIDE | 01a0a5a6-8eae-...
   effective_from 2026-09-15 15:19:11.277371+00  expires_at 2026-09-22 15:19:11.277371+00
  => the override wins while active. PASS.

CASE B3 - THE BASE ROW WAS NOT OVERWRITTEN
    metric     | base_soft | base_hard
   ------------+-----------+-----------
    CALL_MINUTES| 800.0000 | 1000.0000
  => billing.quota_configs still reads 800/1000 while the effective quota is
     2000. The override is a separate layer, not a mutation of the baseline.
     This is the structural difference from the pre-111 behaviour. PASS.

CASE B4 - THE BASELINE STAYS LIVE UNDER AN ACTIVE OVERRIDE
  The commercial baseline was changed to 1000/1200 WHILE the override was active.
        what        | soft_limit | hard_limit
   -----------------+------------+------------
    base_after_change| 1000.0000 |  1200.0000
  Effective quota during the override:
   CALL_MINUTES| 1600.0000 |  2000.0000 | PLATFORM_OVERRIDE
  => the override still wins (2000) and the new baseline is recorded (1200).
     PASS.

CASE B5 - EXPIRY FALLS BACK TO THE *CURRENT* BASELINE  [FAR-P1-05 CLOSED]
  The override window was backdated so the override is expired.
    metric    | soft_limit | hard_limit | unit_label | source | override_id
  ------------+------------+------------+------------+--------+-------------
   CALL_MINUTES| 1000.0000 |  1200.0000 | minutes    | BASE   |
  => 1200, the CURRENT baseline set in B4. NOT 1000 (the stale historical
     baseline from B1-B3) and NOT unlimited (the pre-111 fail-open defect).
     This is the exact regression FAR-P1-05 described, and it does not occur.
     PASS.

CASE B5b - expired override history is RETAINED, not deleted
    metric    | hard_limit | started | expired | not_superseded
  ------------+------------+---------+---------+----------------
   CALL_MINUTES| 2000.0000 | t       | t       | t
  => the row still exists, still non-superseded, simply outside its window. An
     expired override is a historical fact, not a deletion. PASS.

CASE B6 - PERMANENT override (expires_at IS NULL)
   CALL_MINUTES| 2400.0000 |  3000.0000 | minutes | PLATFORM_OVERRIDE | expires_at (null)
  => expires_at IS NULL means permanent: the override applies indefinitely until
     explicitly superseded. PASS.

CASE B7 - override with NULL hard_limit over a FINITE base
    metric    | soft_limit | hard_limit |      source       | overage_allowed
  ------------+------------+------------+-------------------+-----------------
   CALL_MINUTES|           |            | PLATFORM_OVERRIDE | t
  => a NULL effective hard_limit is the representation of "unlimited", and
     overage_allowed is derived as (effective hard_limit IS NULL). A temporary
     uncapping grant is expressible. PASS.

CASE B7b - after the uncapped override expires, the FINITE base returns
   CALL_MINUTES| 1000.0000 |  1200.0000 | BASE | overage_allowed = f
  => fail-CLOSED. An expired "unlimited" grant does not leave the tenant
     permanently uncapped. PASS.

CASE B8 - base with NULL hard_limit and no override (API_REQUESTS)
   API_REQUESTS|            |            | BASE | overage_allowed = t
  => an unlimited COMMERCIAL baseline is still expressible and is reported as
     BASE, not as an override. PASS.

CASE B9 - no base and no override (TTS_CHARACTERS)
    rows_returned
   ---------------
                0
  => the resolver returns ZERO ROWS. It does not invent an unlimited quota and
     does not invent a zero quota. The caller must decide what "unconfigured"
     means; the database does not guess. PASS.

CASE B10 - no base but an ACTIVE override (a pilot grant with no commercial plan)
   TTS_CHARACTERS| 400000.0000 | 500000.0000 | characters | PLATFORM_OVERRIDE
  => an override does not require a pre-existing baseline row. PASS.

CASE B10b - that override expires with NO base underneath
    rows_returned
   ---------------
                0
  => back to zero rows. Expiry of an override without a baseline does NOT
     fabricate a historical base value. No production-data fiction. PASS.

CASE B11 - FAR-P1-05 REGRESSION GUARD ON THE LEGACY COLUMN
  billing.quota_configs.expires_at was set to a window entirely in the PAST:
        what      |        effective_from         |          expires_at           | legacy_window_is_past
   ---------------+-------------------------------+-------------------------------+-----------------------
    legacy_window | 2026-08-16 15:19:11.287536+00 | 2026-09-05 15:19:11.287536+00 | t
  Effective quota:
   CALL_MINUTES| 1000.0000 |  1200.0000 | minutes | BASE
  => the resolver DELIBERATELY IGNORES quota_configs.expires_at. Reading that
     legacy column as "the commercial baseline has disappeared" is precisely the
     fail-open defect FAR-P1-05. The baseline is always the fallback layer,
     whether that legacy column is NULL or in the past. PASS.

CASE B12 - fractional NUMERIC(18,4) limits survive end to end
     metric   | soft_limit | hard_limit |      source
   -----------+------------+------------+-------------------
    STORAGE_GB|     1.2500 |     1.5000 | PLATFORM_OVERRIDE
  => no integer truncation anywhere in the path. PASS.

CASE B13 - NULL organization_id is rejected
  NOTICE: B13 PASS: SQLSTATE=P0001
          MSG=fn_resolve_effective_quota: p_organization_id is required.

  EIGHT-CASE SUMMARY REQUIRED BY THE COVERAGE MATRIX
    1. base only, no override .................... B1   PASS (BASE)
    2. active override over a base ............... B2   PASS (PLATFORM_OVERRIDE)
    3. base changes while override active ........ B4   PASS (override still wins)
    4. override expired, base present ............ B5   PASS (CURRENT base, 1200)
    5. permanent override (expires_at NULL) ...... B6   PASS
    6. override with NULL hard_limit ............. B7   PASS (unlimited while active)
    7. no base, active override .................. B10  PASS
    8. no base, no override ...................... B9   PASS (zero rows)
   plus: expired uncapped override falls back finite (B7b), unlimited BASE (B8),
         expired override with no base (B10b), legacy expires_at ignored (B11),
         fractional limits (B12).

Run as the table owner precisely because no application principal can reach the

-- C.1 starting state (written by Battery D): 100 (superseded), 200 (superseded), 300 (current)

  NOTICE: C.2 PASS: SQLSTATE=23505
          MSG=duplicate key value violates unique constraint "uq_qo_org_metric_current"

-- C.3 a SUPERSEDED historical row may be inserted freely
  NOTICE: C.3 PASS: historical (superseded) rows are not blocked by the partial index

-- C.4 NON-REACTIVATION IS STRUCTURAL: clearing superseded_at on an old row fails
  NOTICE: C.4 PASS: SQLSTATE=23505
          MSG=duplicate key value violates unique constraint "uq_qo_org_metric_current"

    current_rows | history_rows
   --------------+--------------
               1 |            3

-- C.6 supersede + insert is ONE ATOMIC UNIT
  A transaction superseded the current row and was then forced to abort:
    ERROR: C6 forced abort after supersede: new row for relation "quota_overrides"
           violates check constraint "chk_qo_metric_canonical"

    after_hard_limit = 300.0000   source = PLATFORM_OVERRIDE
  => the previously current override is still current. There is no window in

     insert commit together or not at all.

PART 5 - billing.quota_configs IS NOT OVERLOADED; LEGACY COLUMNS ARE MARKED
==================================================================================

111 adds no column to billing.quota_configs and drops none - in particular the
106-era override columns are retained, because dropping them would destroy
historical audit readability. They are instead documented as LEGACY (live
col_description output):

  override_reason : LEGACY (111_5H4). Reason text of the last pre-111 in-place
                    override. Retained for audit readability; not read by
                    billing.fn_resolve_effective_quota(). Override reasons are
                    now billing.quota_overrides.reason.
  effective_from  : LEGACY as override metadata (111_5H4). Kept as the row's own
                    start marker, but the commercial baseline does not expire and
                    the resolver applies no effective-window filter to this table.
                    Override windows are now billing.quota_overrides.effective_from
                    / .expires_at.
  expires_at      : LEGACY (111_5H4). Expiry of the last pre-111 in-place
                    override. billing.fn_resolve_effective_quota() deliberately
                    IGNORES this column: interpreting it as "the base quota
                    disappears" is exactly the fail-open defect FAR-P1-05. NULL or
                    past, the base row is always the fallback layer.
  updated_by      : LEGACY (111_5H4). Platform admin who last set a pre-111
                    in-place override. Retained for audit readability; new
                    override attribution is billing.quota_overrides.created_by.

No pricing field was added to billing.quota_overrides. Quota and price remain
separate concerns.
