5.1 Why the lifecycle guard is stronger than an ACL - and the limit of that

  F.11 re-ran the DEPRECATED -> DRAFT update as the TABLE OWNER and it was
  still refused with the identical message:

        ERROR: voice.agents: illegal lifecycle transition DEPRECATED -> DRAFT
               ... agent id=01a0a945-e5bd-79b9-b4ef-ef169fea25da
        CONTEXT: PL/pgSQL function voice.fn_agents_mutation_guard() line 21 at RAISE

  S.10 confirms what this guard structurally is:

        trg_agents_mutation_guard | CREATE TRIGGER trg_agents_mutation_guard
                                    BEFORE UPDATE ON voice.agents FOR EACH ROW
                                    EXECUTE FUNCTION voice.fn_agents_mutation_guard()
        trg_agents_updated_at     | CREATE TRIGGER trg_agents_updated_at
                                    BEFORE UPDATE ON voice.agents FOR EACH ROW
                                    EXECUTE FUNCTION set_updated_at()

  A BEFORE UPDATE trigger is not an ACL and not an RLS policy. Row level
  security is bypassed outright by a superuser and by any role holding
  BYPASSRLS; a table-level GRANT is irrelevant to the owner. The trigger is
  bypassed by neither. That is why F.11's owner-level refusal is a real
  result and not a restatement of F.4.

  THE HONEST LIMIT OF THAT CLAIM. A trigger binds ordinary DML, including the
  owner's ordinary DML. It does not bind someone who first issues
  ALTER TABLE voice.agents DISABLE TRIGGER trg_agents_mutation_guard, or
  SET session_replication_role = replica, or who drops the trigger. Those are
  DDL and superuser/owner-level acts, and they are outside the application
  guarantee. What F.11 establishes is that the lifecycle contract is enforced
  in the data layer against all normal writes rather than only against
  application-role writes - not that it is unbypassable by a determined owner.

  G.4 (clean re-run, s3_g4_out.txt) - expiry falls back to the CURRENT base:

    G.4.0  current base: ACTIVE_AGENTS | 12.0000 | 15.0000
    G.4.1  override 77/88 installed, expiring in 4 seconds:
             01a0a947-37ae-797b-a623-23e6231bb5ff
    G.4.2  while in force:
             ACTIVE_AGENTS | 77.0000 | 88.0000 | PLATFORM_OVERRIDE |
             expires_at 2026-09-16 08:13:35.946617+00
    G.4.3  sleep past expiry in a transaction of its own;
             now_after_sleep 2026-09-16 08:13:38.00639+00
    G.4.4  resolve in a NEW transaction:
             ACTIVE_AGENTS | 12.0000 | 15.0000 | BASE
    G.4.5  the expired row is still present and still non-superseded:
             01a0a947-37ae-... | 77.0000 | 88.0000 | not_superseded t | expired t

  Expiry returns the organization to the CURRENT commercial baseline (12/15),
  not to a snapshot of what the baseline was when the override was created
  (8/10), and NOT to unlimited. That is precisely the defect FAR-P1-05
  identified and FAR-OD-02 closed, still closed after 112.

  G.4.6 records the window semantics that made the first attempt at this case
  inconclusive:

           now_is_transaction_timestamp | now_is_clock_timestamp
          ------------------------------+------------------------
           t                            | f

  NOW() is transaction_timestamp(), not clock_timestamp(). The effective-window
  predicate is therefore evaluated ONCE per transaction, at transaction start.
  An expiry that falls during a long transaction becomes visible to the NEXT
  transaction, not mid-statement. This is correct and intended behaviour, but
  it must be stated, because a reader who assumes clock_timestamp() would
  misread both the original case G.4 and any future test written the same way.
  See DISCLOSURE 2.

  G.4.7 demonstrates the identical window semantics on the CAPACITY resolver:
          CONCURRENT_CALLS | (null) | (null) | PLATFORM_CAPACITY_OVERRIDE
  The two domains share window semantics; they do not share vocabulary.

  G.5   superseded usage overrides do not reactivate. Eight override rows
        exist for the metric; seven are superseded (not_superseded = f) and
        one is current. The resolver returns:
          ACTIVE_AGENTS | 12.0000 | 15.0000 | BASE
  G.5b  non_superseded_rows = 1. Expiry is a WINDOW test, not a deletion; the
        expired row remains the single current row and simply stops applying.

  G.6   NULL hard_limit remains a valid, EXPLICITLY-unlimited usage override:
          01a0a946-b338-73bd-9318-1859050c9615
          ACTIVE_AGENTS | (null) | (null) | explicitly_unlimited t | PLATFORM_OVERRIDE
  G.6b  and the 110/111 admission guard honours it - a create succeeds past
        the old ceiling: 01a0a946-b36a-7abd-8e6b-6ba665ac5af3, counted = 4.

  G.6 is the usage-domain half of the distinction that FAR_112_02 section 10
  draws for capacity: an EXISTING effective row with hard_limit IS NULL means
  explicitly uncapped, and is a configured decision. It is a different state
  from a resolver that returns zero rows. 112 preserves that distinction in
  both domains.

  H.3   CAPACITY resolver REJECTS ACTIVE_AGENTS:
          ERROR: fn_resolve_effective_capacity_quota: metric ACTIVE_AGENTS is
                 outside the canonical capacity-quota vocabulary (FAR-OD-03).
                 Usage dimensions resolve through billing.fn_resolve_effective_quota().

  H.4   legacy AGENT_COUNT rejected by the USAGE resolver
  H.4b  legacy AGENT_COUNT rejected by the CAPACITY resolver
        Rejected by BOTH. The legacy name is not aliased into either
        vocabulary, as the owner decision requires.

  H.5   NULL metric rejected by the USAGE resolver
  H.5b  NULL metric rejected by the CAPACITY resolver:
          ERROR: fn_resolve_effective_capacity_quota: p_metric is required and
                 must not be NULL.

  H.6   the two vocabulary predicates are disjoint AND NULL-safe:

           metric           | usage_vocab | capacity_vocab
          ------------------+-------------+----------------
           ACTIVE_AGENTS    | t           | f
           CONCURRENT_CALLS | f           | t
           AGENT_COUNT      | f           | f
           (NULL)           | f           | f

        The fourth row is the FAR-P2-08 fix observable. Before the COALESCE
        remediation, p_metric = ANY(ARRAY[...]) returned NULL for a NULL
        input, and a plpgsql IF NOT NULL took its false branch, so the guard
        silently did not fire. Both predicates now return f, not NULL, for a
        NULL metric, and both resolvers raise.

  H.7   concurrent_calls_in_usage_store = 0
  H.7b  active_agents_in_capacity_store = 0

  No row has ever crossed between the two stores. The separation is not only
  enforced at the function boundary; the stores themselves are clean.

  The rejections above are the resolver layer. FAR_112_02 section 11 records
  the other two layers - the table CHECK constraints chk_qo_metric_canonical
  and chk_cqo_metric_canonical, which refuse a cross-domain row even to the
  table owner, and the Platform Admin dispatcher, which routes by domain.
  Domain separation is enforced at three independent layers, not one.

10.1 The single-current-row backstop is structural, not procedural (P8, P8b)

  P8, re-run as the table OWNER so that the ACL is not what refuses:
        NOTICE: second CURRENT row raised [23505] ->
                duplicate key value violates unique constraint "uq_cqo_org_metric_current"

  P8b, a SUPERSEDED historical row with the same (organization, metric):
        NOTICE: superseded historical row accepted -> t (correct)

  uq_cqo_org_metric_current is a PARTIAL unique index (WHERE superseded_at IS
  NULL), so it permits unlimited history while permitting exactly one current
  row. Even the owner, bypassing every function, cannot create a second
  concurrent override. The setter's advisory-lock discipline is the primary
  mechanism; this index is the backstop underneath it.

  The first P8 attempt (post112_b_out.txt) returned 42501 permission denied
  rather than 23505, because it ran as app_platform_admin, which holds no
  INSERT. That attempt proved an ACL, not an index. It was re-run as owner to
  reach the index. See DISCLOSURE 4.

10.5 AUDIT ATOMICITY - the audit write is in the same transaction

  This property had no captured negative-path evidence in any earlier run, so
  a targeted probe was written and executed (s3_aud.sql / s3_aud_out.txt). It
  performs no schema change and leaves no residue.

  T.0  identity: session_user app_platform_admin, is_platform_admin = t

  T.1  baseline:
         audit_rows_before 13 | capacity_rows_before 7

  T.2  the guarded setter called INSIDE an explicit transaction:
         new_id 01a0a961-b58b-78a2-b656-56fa9a226b62
         audit_rows_in_tx 14 | capacity_rows_in_tx 8

==================================================================================
11. THE EXACT SCOPED SECURITY GUARANTEE
==================================================================================

  This section states precisely what is and is not guaranteed. Imprecision
  here was itself a finding (FAR-P3-04), so the wording is deliberate.

11.1 What actually enforces the capacity-quota mutation contract

  The contract is enforced by a combination of mechanisms, each independently
  observed above:

    (a) A guarded SECURITY DEFINER function as the sole sanctioned write path.
        billing.fn_platform_set_quota_override is the only function permitted
        to write billing.capacity_quota_overrides. S.3.

    (b) An explicit, non-inheritable search_path on that function:
        search_path=billing, organization, pg_catalog. A SECURITY DEFINER
        function without this is vulnerable to search_path capture by its
        caller. S.3.

    (c) Minimum EXECUTE grants. Exactly one role - app_platform_admin - can
        execute the setter, and app_api is explicitly REVOKEd because the
        function is CREATE OR REPLACEd and a replace preserves the prior ACL.
        S.5, R6, 112_5H5.sql:737.

    (d) No PUBLIC EXECUTE on any function 112 created or replaced, and no
        PUBLIC privilege of any kind on any governed quota table. S.4, S.7.

    (e) No raw runtime DML path. No application role holds INSERT, UPDATE or
        DELETE on the capacity store. The guarded function is not merely the
        preferred path; it is the only one available to any app role.
        S.9, R5.

    (f) In-function validation before any write: organization existence,
        actor identity, metric membership in the correct governed vocabulary,
        reason length, limit ordering, and future expiry. Observed at T.4
        (vocabulary), at the s3_aud first run (organization existence), and
        across FAR_112_02 sections 11 and 12.

    (g) Transactional atomicity of the row write and its audit event, proven
        in both directions at T.2/T.2b/T.3 and T.4.

    (h) A structural single-current-row backstop that binds even the table
        owner: the partial unique index uq_cqo_org_metric_current, 23505 at
        P8.

    (i) Row level security, ENABLEd and FORCEd, for ordinary tenant read
        isolation: a tenant sees only its own organization's rows. S.8, R7.

    (j) For the Agent path specifically, a BEFORE UPDATE TRIGGER rather than
        an ACL, so the lifecycle and anti-resurrection rules bind ordinary
        DML by the table owner as well. F.11, S.10.

11.2 The hardened Platform Admin predicate

  S.11 captures organization.is_platform_admin() as it exists in the database:

        CREATE OR REPLACE FUNCTION organization.is_platform_admin()
         RETURNS boolean
         LANGUAGE sql
         STABLE
        AS $function$
          SELECT session_user = 'app_platform_admin'
             AND COALESCE(current_setting('app.is_platform_admin', true), 'false') = 'true'
        $function$

  Two conditions are required together: the session must be CONNECTED AS
  app_platform_admin, and the request-scoped GUC must be set. The session_user
  half cannot be forged by setting a GUC, because session_user does not change
  after SET ROLE. A session connected as postgres therefore CANNOT satisfy
  this predicate and cannot pass the platform-admin RLS policy, regardless of
  its superuser status.

  That is a real, tested property and it is the correct thing to say. Note
  also that this function carries no SET search_path clause of its own; it is
  fully schema-qualified in its references and depends on no schema resolution.

11.3 What is NOT claimed

  The following statements are FALSE and are not made anywhere in this
  reconciliation:

    * "PostgreSQL superuser privilege cannot be bypassed."
      It can. S.1 shows postgres with rolsuper = t. A superuser can disable
      triggers, drop constraints, alter functions, read and write any table,
      and set any GUC.

    * "FORCE ROW LEVEL SECURITY binds a postgres-owned SECURITY DEFINER
      function against superuser bypass."
      It does not. FORCE removes the OWNER's exemption from RLS for ordinary
      DML. It has no effect on a superuser, who bypasses RLS entirely and
      unconditionally. This was the specific imprecision recorded as
      FAR-P3-04.

    * "No role can bypass RLS on the quota tables."
      Two application roles hold BYPASSRLS (app_migration, app_platform_admin,
      both from 001_5B.sql:41 and :44), and postgres holds it as a superuser.
      S.1, S.2.

    * "The lifecycle trigger is unbypassable."
      It binds all ordinary DML including the owner's (F.11). It does not bind
      ALTER TABLE ... DISABLE TRIGGER, SET session_replication_role = replica,
      or DROP TRIGGER.

11.4 The guarantee, stated exactly

  Within the application's runtime trust boundary - that is, for every session
  connecting as one of the eight non-superuser application roles listed at
  S.1, which is how the application, its workers and its administrators
  actually connect - the capacity-quota mutation contract is enforced by
  mechanisms (a) through (j) of 11.1, and no such session can:

      * write billing.capacity_quota_overrides other than through the guarded
        function (S.9, R5),
      * execute that guarded function without being app_platform_admin
        (S.5, R6),
      * create a second concurrent override for one (organization, metric)
        (P8),
      * write a cross-domain row into either override store (H.1-H.7b, and
        the CHECK constraints at FAR_112_02 section 11),
      * commit an override without its audit event, or leave an audit event
        behind for a refused or rolled-back override (T.2b, T.3, T.4),
      * read another tenant's override rows through the tenant read path
        (R7),
      * or, on the Agent path, effect an illegal lifecycle transition, a
        tenant-ownership transfer, or a soft-delete resurrection (F.4-F.8).

  DELIBERATE SUPERUSER OR TABLE-OWNER ACTION IS OUTSIDE THIS GUARANTEE. A
  session with superuser privilege, or one holding the table owner role, can
  disable triggers, drop constraints and indexes, replace function bodies, and
  write any table directly. Nothing in migration 112 - and nothing available
  at the PostgreSQL level - prevents that. Protection against that class of
  action belongs to credential custody, connection policy, network
  segmentation and infrastructure audit, not to this schema. This
  reconciliation does not claim otherwise, and any downstream document that
  states or implies otherwise should be corrected against this section.

DISCLOSED HARNESS LIMITATIONS AND CORRECTIONS
==================================================================================

  DISCLOSURE 1 - case D.2 is mislabelled in the captured output.
    The header reads "clones of far112-B1 (EXPECT: exactly 1 new row)" and the
    result is rows_named_b1 = 2. The query counts every row NAMED far112-B1,
    which includes the clone SOURCE created at B.2 as well as the single
    clone. The probe's expectation statement is wrong; the migration is not.
    The clone one-winner invariant is carried by D.3 (counted = 3, never 4),
    by the single agent_id returned across the two racing sessions, and by the
    D.4 inventory showing exactly two far112-B1 rows. Section 3 quotes D.2 in
    full alongside this correction rather than transcribing it as though it
    had returned 1.

  DISCLOSURE 2 - case G.4 in s3_gh_out.txt is a single-snapshot artifact.
    The original G.4 slept past the override expiry and then re-resolved, but
    both statements were sent in one psql -c string and therefore ran in one
    implicit transaction. Because NOW() is transaction_timestamp(), the
    effective window was evaluated once at transaction start, before the
    sleep, and the captured line still reads
    33.0000 | 44.0000 | PLATFORM_OVERRIDE. That line does NOT show a failure
    to expire and must not be read as one. The case was re-run with each
    statement in its own transaction (s3_g4_out.txt), producing G.4.4
    12.0000 | 15.0000 | BASE, and the underlying semantics were proven
    directly at G.4.6 (now_is_transaction_timestamp t,
    now_is_clock_timestamp f). Section 6 cites the re-run and G.5, not the
    original G.4 line.

  DISCLOSURE 3 - the S.2 column label asserts an expectation the data
    contradicts.
    I named the column bypassrls_app_roles_must_be_0 and it returned 2. The
    label encodes an expectation I had not verified before writing the probe.
    The data is correct: app_migration and app_platform_admin both hold
    BYPASSRLS, from 001_5B.sql:41 and 001_5B.sql:44 respectively. Rather than
    drop the column or re-run the probe with a friendlier label, the wrong
    label is reproduced in section 8.7 next to the provenance grep, and the
    claim actually made is narrowed to what is true: 112 added no new BYPASSRLS
    role and granted BYPASSRLS to no role. 112_5H5.sql contains no role
    statement of any kind.

  DISCLOSURE 4 - the first P8 probe measured an ACL, not the index.
    Attempt 1 (post112_b_out.txt) ran as app_platform_admin and returned
    42501 permission denied for table capacity_quota_overrides. That is a
    correct and useful result - it independently corroborates S.9 - but it
    does not prove the partial unique index, because the statement never
    reached it. P8 was re-run as the table owner (post112_c_out.txt) and
    returned 23505 against uq_cqo_org_metric_current. Section 10.1 quotes the
    owner re-run and records the first attempt.

  DISCLOSURE 5 - the audit-atomicity probe was first pointed at the wrong
    instance.
    s3_aud.sql was initially executed against far112_fresh, which holds the
    schema but no fixture rows (audit_rows_before 0, capacity_rows_before 0),
    and the setter refused with "fn_platform_set_quota_override: organization
    00000000-0000-7000-8000-00000000a001 not found." from its in-function
    existence validation. All behavioural fixtures live in far112_incr. The
    probe was re-pointed there and produced the T.1-T.5 results in section
    10.5. The first run is retained in the record because its failure mode is
    itself evidence of the organization-existence validation.

  DISCLOSURE 6 - structural evidence and behavioural evidence come from
    different instances.
    S.1-S.11 were captured against far112_fresh; every behavioural case was
    captured against far112_incr. Rather than assume the two agree, s3_sec.sql
    was re-run unchanged against far112_incr and the outputs compared byte for
    byte after trailing-whitespace normalisation. They are identical. This is
    recorded as a disclosure rather than buried, because a reader is entitled
    to know that the ACL table in section 8 and the tenant behaviour in
    section 9 were not observed in the same database.

  DISCLOSURE 7 - the fixture state is cumulative across the battery.
    Cases A through H ran in sequence against one database and each case
    inherits the state the previous case left. Absolute row counts and
    override histories therefore reflect the whole battery, not the case being
    read. Every case that depends on a starting condition establishes and
    prints that condition first (A.0c counted = 0; C.0 slots_remaining = 1;
    D.0b slots_remaining = 1; E.0b agents_total_before = 5; G.4.0 the current
    base; T.1 the baseline counts). Counts should be read as deltas against
    those printed baselines.

  NOT A LIMITATION, BUT STATED FOR THE REVIEWER.
    Case F.11 and case P8 were deliberately run as the TABLE OWNER, not as an
    application role. This was not an oversight and not an attempt to make a
    result look stronger. Both cases exist specifically to test mechanisms
    that are claimed to bind the owner - a BEFORE UPDATE trigger and a partial
    unique index - and running them as a role that would have been stopped
    earlier by an ACL would have proven nothing about those mechanisms. The
    scope and the limits of what owner-level binding means are stated in 5.1
    and 11.3.
