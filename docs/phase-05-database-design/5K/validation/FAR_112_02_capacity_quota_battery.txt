SECTION 2 - NULL SAFETY OF BOTH CATALOG HELPERS  (FAR-P2-08 closure)
==================================================================================

  THE DEFECT. Before 112, the canonical-metric guard was written as

      IF NOT billing.fn_is_canonical_usage_metric(p_metric) THEN RAISE ...

  and the helper evaluated `p_metric = ANY(ARRAY[...])`. Under SQL
  three-valued logic a NULL input makes that expression NULL, not FALSE;
  `NOT NULL` is NULL; and a plpgsql IF on NULL takes the FALSE branch. The
  guard therefore silently did not fire on NULL and execution fell through.

  A. both helpers now return a real FALSE - not SQL NULL - for NULL input

   usage_null | usage_is_sql_null | cap_null | cap_is_sql_null
  ------------+-------------------+----------+-----------------
   f          | f                 | f        | f
  (1 row)

  Both helpers return f (false), and neither return value is SQL NULL. The
  COALESCE(..., FALSE) wrapper is what produces this.

  A2 (NOTICEs from the same run). the plpgsql NOT-guard now FIRES

   NOTICE:  plpgsql NOT-guard now FIRES for usage helper on NULL  -> t
   NOTICE:  plpgsql NOT-guard now FIRES for capacity helper on NULL -> t

  This is the assertion that matters. It is not enough that the helper
  returns false; the calling `IF NOT ...` must actually enter its raising
  branch. Both do.

  B. both RESOLVERS reject NULL loudly, so there is no 0-row fail-open

   NOTICE:  usage resolver(NULL)    raised [P0001] -> fn_resolve_effective_quota: metric <NULL> is outside the canonical 5H §11.1 usage-dimension vocabulary.
   NOTICE:  capacity resolver(NULL) raised [P0001] -> fn_resolve_effective_capacity_quota: p_metric is required and must not be NULL.

  Both raise. They raise with different messages because the capacity
  resolver validates p_metric IS NULL explicitly before consulting the
  vocabulary, which produces the more precise message; the usage resolver
  reaches the vocabulary check with a NULL that the COALESCE now renders
  FALSE. Both outcomes are correct and neither returns zero rows.

  This distinction matters for section 15: a NULL metric is a CALLER DEFECT
  and raises. Zero rows is a CONFIGURATION STATE and does not raise. They
  must not be conflated by a consumer.

  P1. the Platform Admin dispatcher also rejects NULL BY NAME

   NOTICE:  NULL metric      raised [P0001] -> fn_platform_set_quota_override: p_metric is required and must not be NULL.

  At head 111 this same probe produced a raw [23502] not-null violation from
  the storage layer. It is now a named application-level error raised before
  any write is attempted.

  Source: post112_a_out.txt blocks A, A2, B; post112_b_out.txt block P1.

==================================================================================

  Each capacity override is its own row in billing.capacity_quota_overrides.
  billing.quota_configs is never written by the override path, so the
  commercial baseline is never destroyed in place - the 112 capacity analogue
  of the FAR-P1-05 remediation 111 made for usage.

  B (resolver battery). an active override wins over BASE

             source           | soft_limit | hard_limit | permanent
  ----------------------------+------------+------------+-----------
   PLATFORM_CAPACITY_OVERRIDE |    70.0000 |    80.0000 | t
  (1 row)

  G. a LOWER override than the base IS honoured

             source           | soft_limit | hard_limit
  ----------------------------+------------+------------
   PLATFORM_CAPACITY_OVERRIDE |     5.0000 |     8.0000
  (1 row)

  The base for this organization was 45/50. An override of 5/8 takes effect.
  An override is admission control in both directions; the commercial base is
  not a floor. For a capacity quota this is the operationally important
  direction: it is how an operator throttles a tenant that is degrading

SECTION 5 - EXPIRY FALLBACK
==================================================================================

  D (resolver battery). an EXPIRED override falls back to the CURRENT base -
     never to unlimited, never to a stale snapshot

   source | soft_limit | hard_limit | fail_open_unlimited
  --------+------------+------------+---------------------
   BASE   |    45.0000 |    50.0000 | f
  (1 row)

   rows_returned_must_be_1
  -------------------------
                         1
  (1 row)

  Both halves are required. source = BASE proves the fallback target, and
  rows_returned = 1 proves the resolver did not simply go silent. An expired
  capacity override degrades to the commercial baseline, which is a real
  finite ceiling.

  TIME SEMANTICS - REPORTED BECAUSE IT CHANGES THE CONTRACT.
  The effective-window predicate uses NOW(), which in PostgreSQL is
  transaction_timestamp(), not clock_timestamp(). It is therefore evaluated
  once per transaction, at transaction start. Proven directly:

   now_is_transaction_timestamp | now_is_clock_timestamp
  ------------------------------+------------------------
   t                            | f
  (1 row)

  The operative consequence: a reported capacity quota is STABLE for the
  duration of a transaction, and an expiry becomes visible to the NEXT
  transaction. This already matches the documented usage-domain behaviour at
  6K:3579 and is now confirmed for capacity. A long-running transaction will
  not observe an expiry mid-flight. For a reservation-based capacity contract
  this is a feature, not a hazard - see 6K section 54 - but it must be stated,
  because a consumer that assumed wall-clock evaluation inside a transaction
  would be wrong.

  The live expiry transition, executed with each statement in its OWN
  transaction (see DISCLOSURE 1):

   G.4.0  before      ACTIVE_AGENTS | 12.0000 | 15.0000 | BASE
   G.4.1  override created 01a0a947-37ae-797b-a623-23e6231bb5ff
   G.4.2  in force    PLATFORM_OVERRIDE 77.0000 / 88.0000,
                      expires_at 2026-09-16 08:13:35.946617+00
   G.4.3  after sleep now = 2026-09-16 08:13:38.00639+00   (past the expiry)
   G.4.4  after       ACTIVE_AGENTS | 12.0000 | 15.0000 | BASE
   G.4.5  the expired row is still present: not_superseded = t, expired = t

  G.4.5 is the point most easily missed: the override row is NOT deleted and
  NOT marked superseded. It simply falls outside its effective window. The
  row remains auditable history.

  E. a base changed WHILE the override was alive -> the NEW base takes over
     at expiry (see section 6).

  Source: post112_d_out.txt block D; s3_g4_out.txt blocks G.4.0 - G.4.6.

SECTION 7 - PERMANENT OVERRIDE
==================================================================================

  B. an override with expires_at IS NULL is permanent-until-superseded

             source           | soft_limit | hard_limit | permanent
  ----------------------------+------------+------------+-----------
   PLATFORM_CAPACITY_OVERRIDE |    70.0000 |    80.0000 | t
  (1 row)

  permanent = t is the computed expires_at IS NULL flag. Such a row never
  falls out of its effective window; the only way it stops applying is
  supersession by a later override (section 8).

  NOTE ON TWO DIFFERENT NULLS. expires_at IS NULL means "no end date". It is
  a different column and a different meaning from hard_limit IS NULL, which
  means "explicitly uncapped" (section 10). A row can be one, the other,
  both, or neither. They must not be conflated.

SECTION 10 - NULL hard_limit = EXPLICITLY UNCAPPED  (and what it is NOT)
==================================================================================

  H. a NULL hard_limit on an ACTIVE capacity override is REPORTED as a row,
     not inferred from an empty result

             source           | soft_limit | hard_limit | explicit_row
  ----------------------------+------------+------------+--------------
   PLATFORM_CAPACITY_OVERRIDE |            |            | t
  (1 row)

  explicit_row = t. A row EXISTS. Its hard_limit is SQL NULL. This is the
  only state that authorises admission without a ceiling, and it is an
  affirmative, auditable, Platform-Admin-authored decision recorded in a row
  that names who set it and why.

  THE DISTINCTION THIS SECTION EXISTS TO ESTABLISH - required explicitly by
  Stage 3+ section 3, and carried into 5H, 6D, 6K and the Final
  Reconciliation:

      hard_limit IS NULL on an EXISTING effective row
          = EXPLICITLY UNCAPPED. A configuration decision was made.
            Admission proceeds without a ceiling.

      the resolver returning ZERO ROWS
          = CAPACITY CONFIGURATION ABSENT OR INVALID. No decision was made.
            This is NOT "unlimited" and MUST NOT be read as unlimited.
            See section 15.

  Z.5. the discriminator a consumer must branch on, all three states in one
       result set

                  label                | row_present | hard_limit |           source
   -------------------------------------+-------------+------------+----------------------------
    A: active override, hard_limit NULL | t           |            | PLATFORM_CAPACITY_OVERRIDE
    B: no base row, no override         | f           |            |
    C: finite configured base           | t           |    10.0000 | BASE
   (3 rows)

  row_present separates {A, C} from B. hard_limit IS NULL separates A from C.
  Note that the hard_limit COLUMN renders identically blank for A and for B -
  which is exactly the trap. A consumer that reads only hard_limit, or that
  applies COALESCE(hard_limit, 'infinity') to a result set, cannot tell them
  apart: over a zero-row result set there is no row for COALESCE to act on at
  all, and an `IF NOT FOUND THEN RETURN` consumer reads that as unlimited.
  That is the fail-open this case exists to forbid.

  Z.6. the SAME three-state distinction exists on the USAGE resolver

             label           | row_present | hard_limit | source
   --------------------------+-------------+------------+--------
    usage org1 ACTIVE_AGENTS | t           |    15.0000 | BASE
    usage org3 ACTIVE_AGENTS | f           |            |
   (2 rows)

  The rule is domain-symmetric. It is not a capacity special case, and it
  matches the already-documented usage-domain statement at 6K:3570 that no
  row is "not a synonym for unlimited; it is the absence of a configured
  limit".

  Source: post112_d_out.txt block H; s3_z_out.txt blocks Z.2 - Z.6.

SECTION 11 - USAGE / CAPACITY DOMAIN REJECTION (BOTH DIRECTIONS)
==================================================================================

  The two domains must not silently collapse into one another. Rejection is
  proven at three independent layers.

  LAYER 1 - THE RESOLVERS.

   NOTICE:  usage resolver(CONCURRENT_CALLS)  raised [P0001] -> fn_resolve_effective_quota: metric CONCURRENT_CALLS is outside the canonical 5H §11.1 usage-dimension vocabulary.

   NOTICE:  capacity resolver(ACTIVE_AGENTS)  raised [P0001] -> fn_resolve_effective_capacity_quota: metric ACTIVE_AGENTS is outside the canonical capacity-quota vocabulary (FAR-OD-03). Usage dimensions resolve through billing.fn_resolve_effective_quota().

  Each resolver rejects the other domain's metric, and the capacity
  resolver's message names the correct function to use instead. Both RAISE
  rather than returning zero rows, because zero rows from a metric the caller
  believes is valid is precisely the fail-open condition.

  LAYER 2 - THE STORAGE, tested as the table OWNER so that a CHECK
  constraint, not an ACL, is what fails:

   NOTICE:  quota_overrides <- CONCURRENT_CALLS raised [23514] -> new row for relation "quota_overrides" violates check constraint "chk_qo_metric_canonical"

   NOTICE:  capacity_quota_overrides <- ACTIVE_AGENTS raised [23514] -> new row for relation "capacity_quota_overrides" violates check constraint "chk_cqo_metric_canonical"

  Domain separation is STRUCTURAL. A CONCURRENT_CALLS row cannot be placed in
  the usage override store, and an ACTIVE_AGENTS row cannot be placed in the
  capacity override store, by ANY principal including the table owner. This
  discharges the FAR-OD-03 instruction "Do NOT put CONCURRENT_CALLS rows into
  billing.quota_overrides" as an enforced constraint rather than a convention.

  LAYER 3 - THE DISPATCHER. See section 12 (P2, P4).

  Source: post112_a_out.txt blocks D and F.

15.2  THE FINDING THAT MUST NOT BE SMOOTHED OVER

  Z.15f. the RESOLVER conflates "configuration absent" with
         "organization does not exist"

                 state               | rows_returned
   ----------------------------------+---------------
    existing org, no capacity config |             0
    non-existent organization        |             0
   (2 rows)

  The capacity resolver validates tenant CONTEXT; it does not validate
  organization EXISTENCE. An existing-but-unconfigured organization and a
  wholly non-existent organization are INDISTINGUISHABLE at the resolver's
  return value - both are zero rows, and neither raises.

  The guarded WRITE path DOES distinguish them (section 12, Z.16f): it
  rejects a non-existent organization by name.

  This asymmetry is reported, not smoothed over, and it STRENGTHENS the
  fail-closed requirement rather than weakening it. Because the read path
  cannot tell "you have no capacity configured" from "you do not exist", a
  consumer has no basis whatsoever for treating zero rows as permission to
  proceed. Neither of the two states it might be in is a state in which
  unlimited concurrent calls were authorised.

  Z.17f. zero rows was a CONFIGURATION STATE, not a defect. The same
         organization, once configured through the guarded path, resolves
         normally:

        metric      | soft_limit | hard_limit |           source
   ------------------+------------+------------+----------------------------
    CONCURRENT_CALLS |     3.0000 |     7.0000 | PLATFORM_CAPACITY_OVERRIDE
   (1 row)

  Z.18f. the four distinguishable capacity states coexisting in one instance

                             label                           | row_present | hard_limit |           source
   -----------------------------------------------------------+-------------+------------+----------------------------
    A: active override, hard_limit NULL = EXPLICITLY UNCAPPED | t           |            | PLATFORM_CAPACITY_OVERRIDE
    B: finite configured BASE                                 | t           |    10.0000 | BASE
    C: finite configured OVERRIDE                             | t           |     7.0000 | PLATFORM_CAPACITY_OVERRIDE
    D: NO CONFIGURED CAPACITY QUOTA (zero rows)               | f           |            |
   (4 rows)

15.3  THE NORMATIVE INVARIANT

  NO CONFIGURED HARD CAPACITY QUOTA MUST NOT FAIL OPEN.

  For CONCURRENT_CALLS this is a HARD CAPACITY ADMISSION CONTRACT. Stated as
  consumer rules:

    (1) row_present = FALSE (resolver returned zero rows) means CAPACITY
        CONFIGURATION ABSENT OR INVALID. It MUST NOT be described as
        "unlimited" and MUST NOT admit a concurrent call.
    (2) A row present with hard_limit IS NULL means EXPLICITLY UNCAPPED.
        This, and only this, authorises admission without a ceiling.
    (3) A row present with a finite hard_limit is the ceiling. It is never
        rounded; NUMERIC(18,4) fractional limits are compared as stored.
    (4) A NULL metric, or a metric outside the governed vocabulary, is a
        CALLER DEFECT and raises. It is not a configuration state.

  These are distinct outcomes and a consumer must branch on all four.

15.4  WHERE THE FAIL-CLOSED DECISION LIVES

  Z.7 establishes that the SQL layer returns cleanly on zero rows. The
  resolver deliberately does not raise, because "this organization has no
  configured capacity" is a legitimate, reportable configuration state that a
  6M administrative read must be able to display without an exception.

  The fail-closed decision therefore belongs to the CONSUMER contract - 6D
  call admission, 6H campaign dispatch, and the 6K capacity authority that
  both consume. That is precisely why Stage 3+ section 3 requires it written
  down rather than left implicit, and it is written down in 6K section 54,
  6D and 6H by this pass.

15.5  NO NEW PUBLIC ERROR CODE WAS INVENTED

  The existing contracts already cover this case and are REUSED:

    * 6A section 24.2 already defines the error family
      DEPENDENCY_UNAVAILABLE, mapped to 503 by 6A section 7.4 and 6A:148
      ("Dependency failure surfaced honestly, not masked as 500").
    * 6H:529 and 6H:1772 already establish the pattern for a missing
      configuration hard stop: 503 DEPENDENCY_UNAVAILABLE carrying a
      details.reason discriminator (there, COMPLIANCE_POLICY_NOT_FOUND),
      described as "fail-closed, never a permissive default". The capacity
      analogue takes a reason discriminator on the existing code rather than
      a new top-level code.
    * 6H:1189 already states the fail-closed rule for CONCURRENT_CALLS
      verbatim: if the quota source "is unreachable when a pre-flight or
      dispatch check needs it, the platform fails closed (treat as
      quota-exhausted, DEFERRED, never ELIGIBLE by default)". The campaign
      path therefore needs no synchronous client error at all - failing
      closed means DEFERRED.
    * 6K:3570 already states the "no row is not a synonym for unlimited"
      rule for the USAGE domain. Capacity reuses the identical framing.

  IMPLEMENTATION-READINESS, DISCLOSED AS DEFERRED, NOT AS CLOSED.
  The exact public error mapping for the synchronous 6D call-admission path -
  specifically the literal details.reason token - remains
  implementation-specific and is carried as implementation-readiness in the
  handoff ledger. The NORMATIVE INVARIANT above is NOT deferred: it is
  binding now, in every consumer, regardless of how the reason token is
  finally spelled.

  DISCLOSURE 1 - the original G.4 expiry probe was a single-snapshot
  artefact, and its result was NOT used.
    The original G.4 placed `SELECT pg_sleep(5);` and the resolver query in

    one snapshot, so the resolver still reported the pre-expiry
    PLATFORM_OVERRIDE 33/44 even though wall-clock time had passed the

    112. The probe was re-run as s3_g4.sh with each statement in its own -c
